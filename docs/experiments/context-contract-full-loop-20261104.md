# 来源展示、计划完整循环与历史分工：第二轮实验

日期：2026-11-04。用户要求三项分别实验，必须配备真实循环、追问和回读条件，再考虑组合；尤其关注文末来源是否合适、计划阶段究竟如何工作，以及旧助手内容应如何处理。

## 结论

普通学习解释可以采用“自然提及文件/章节＋程序文末查阅来源”，但查阅列表不能冒充逐句支持；精确引文、来源冲突与重要事实仍须能回到具体原文。阶段化适合减少无关操作和厘清输入，但不意味着另起一个模型一次生成答案。历史不能按human/ai角色一刀切：旧助手断言是待核对内容，旧助手草稿却可能是本轮编辑对象，程序确认结果则是执行事实。

实验侧已把只读取证、结果反馈、澄清后续轮次、校验纠错、确认保存及新进程恢复连通。组合初版仍在恢复回答中错误否认当前计划，状态输入修订后同快照复验与完整闭环的核心信息正确。所有候选仅在tests，尚未落地业务。

## 外部依据（本轮实际查阅）

- [LlamaIndex CitationQueryEngine](https://developers.llamaindex.ai/python/examples/query_engine/citation_query_engine/)同时展示正文编号引用与可独立查看的source_nodes；来源集合与正文引用不是同一件事。其示例使用较早模型，本轮借鉴接口分工，不移植模型配置，也不将它称为最新效果证明。
- [Claude原生引用](https://platform.claude.com/docs/en/build-with-claude/citations)将文字块与文档位置关联，说明精细关联仍有独立价值。本项目没有切换提供商或假设Qwen支持该原生能力。
- [Open Deep Research源码](https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/deep_researcher.py)分开clarify_with_user、write_research_brief、research_supervisor、final_report_generation；借鉴阶段职责，不照搬Supervisor或新增多个Agent。
- [LangChain context engineering](https://docs.langchain.com/oss/python/langchain/context-engineering)区分临时模型上下文与持久状态，并按任务阶段选择工具。沿用前轮Deep Agents可回读外置、Pi近期保留/上下文投影的参考。外部实现不保证本项目收益。

## 实验一：自然章节说明＋程序文末列表

baseline使用原流程；footer只在请求副本隐藏资料读取citation，让模型自然提及文件或章节，原始回执仍用于执行、审计和程序展示。程序只收集实际成功读取，不把目录、搜索位置、失败文件写成已读证据；去重并保留截断/部分行提示。

```python
panel = footer_sources(trace.get("tool_results", []))
if panel:
    text += "\n\n" + panel
```

标题为“程序列出的本轮查阅资料；不表示每项资料都支持回答全部论断”。规范缺失不补造来源，确认记录与文档引用分开标明。历史来源用程序实际citation生成，模型无需复制UUID。

结果：2个footer条件均正确列出实际查阅来源；章节边界条件仅列handbook，没有把未读规范列入。两组核心判断均能区分预算/完成、手册/规范，但质量不能只看核心结论：

- 来源冲突baseline先正确说120分钟不可分段，后又建议3×40分钟，违反资料要求。footer没有提出物理中断，却用了“心理阶段每30分钟节点”的措辞，容易歧义，应说明仍连续执行。这是小样本观察，不归因为文末模式消除了错误。
- 章节边界baseline错误调用propose_learning_feedback，参数校验拒绝后仍说“您的反馈已记录”。未发生实际写入，但用户交付事实失实。footer此样本没有该行为，不能据此认定footer改善操作判断。
- baseline累计输入32220、footer32178；后者一次真实空响应恢复，额外消耗一次请求，前者另一条件多走错误操作。不能把总数接近或减少42token解释为同质节省。

结论：支持普通问答采用文末查阅列表作为默认展示，模型可自然说明“第三章/第七章”。不默认精确逐句编号，不将查阅列表称为逐句依据。需要核对某条断言、来源矛盾、逐字引文时仍应给出可追溯片段；“第七章说xxx”本身也要核对。操作结果同样应由程序提供可靠展示，不能把“模型说已记录”当执行事实。

## 实验二：完整计划循环，而非一次生成

入口在本实验由调用方明确选择计划准备阶段，不评价自动意图路由。该阶段继续使用生产_main._invoke_interactive_turn：

```text
真实状态＋历史＋当前请求
  → 模型决定
     → 只读工具 → 真实结果/错误回传 → 再决定（原总预算）
     → 信息不足 → 澄清 → 用户补条件 → 下一轮重新进入
     → 候选结果 → 原inbox校验 → 错误可修正/合法则pending
     → 程序展示与n/y确认 → 原保存机制
```

阶段只绑定资料/历史只读工具和finish_plan_request，不绑定反馈、建任务、取消任务等写操作；不是禁止必要取证。终结schema有candidate/clarification/infeasible/no_change，candidate由程序调用原PlanProposalInbox登记，不从普通文本猜候选。非候选工具结果由程序交付explanation，不再请求模型复制；这是程序事件，不算一次真实生成。

| 场景 | 原流程模型调用/输入 | 阶段模型调用/输入 | 实际结果 |
|---|---:|---:|---|
| 读资料再候选 |3 / 13381|3 / 8293|两组真实读取后提交，拒绝状态不变|
| 缺规范 |3 / 13325|5 / 14911|两组说明缺失；阶段实际读缺失文件、又查反馈，最终clarification|
| 先澄清后补充 |4 / 18224|4 / 11545|两组第一轮不提交，补充20分钟后读取并提交；阶段结果clarification→candidate|
| 观察冲突 |4 / 18311|4 / 11527|两组核对后回答不可行、未提交；阶段直接普通文本结束，没有终结枚举|

候选取证的工具序列为list_material_files→read_material_lines→finish_plan_request，实际执行且同一个预算循环。读取规范条件则沿handbook→observation_protocol继续。没有预设首批工具，没有替模型补查。缺失条件表明不是只给“充分证据”才测试。

阶段正例输入较少，但输出和耗时未稳定下降：读资料候选约15.32→24.28秒，缺失约10.73→33.31秒，澄清全链约20.26→28.10秒。不能称提速。

离线另外用真实循环/真实本地读取验证：候选登记与拒绝、错误空正文回传后修正、no_change程序交付不额外调用模型。真实模型实验不注入这些替身，它们只验程序循环条件。

契约判断：普通冲突回答对用户是正确交付，但没有满足“所有结果均结构化”的实验契约。正式设计可只把会影响状态的候选强制结构化，普通澄清/解释保留自然回复，不为收集枚举再增加格式束缚。并未把此条偷偷改成枚举通过。

## 实验三：旧历史不是按角色一刀切

对比baseline完整历史、drop隐藏旧问答、typed保留用户原话及可识别程序回执而移走助手正文。三组都保留归档查询能力。

先发现一条隐形历史通道：feedback_proposal_sources还会附带最近用户消息。drop/typed同时去掉该表的旧原话，保留当前输入；typed另保留真实用户消息，避免“删历史后仍记住”只是从旁路看到相同内容。此变换只作用模型请求，不改真实来源索引或持久记录。

| 场景 | 完整历史 | 全隐藏 | 用户＋回执 |
|---|---|---|---|
| 旧助手错建议 | 查规范，明确未采用并承认旧建议错 | 查规范正确，但只说无法核实采用，没有利用归档中的用户明确否定 | 查规范正确，保留用户原话却仍弱化为没有证据采用 |
| 用户20→35更正 |1次生成/4433输入，35分钟正确|5次/24121，通过搜索回读恢复35与活动方式|3次/14298，35分钟正确，但额外查资料且有重复说明|
| 旧候选只有普通文本 |1次/4400，准确改第二项|5次/23835，先查确认再搜索回读，完成|2次/8873，查不到确认回执后向用户索取旧候选，未提交|

不是所有助手文字都该删除：错误断言是待核对说法，草稿却可能是当前编辑对象。也不是用户条件都该只存回查：短会话移走35分钟更正反而显著增加调用。少输入、失败或少回答不能当成本改善。

### 定位与程序回执的补验

- typed_locator为移走的旧助手正文附真实source_index/turn_number，来自本次实际归档映射，不让模型猜位置。相同旧候选请求变为read_conversation_turn→propose_plan_change，2次生成/9189输入，准确保留12分钟与8分钟。比全隐藏5次便宜，但仍比完整短历史1次贵。
- receipt条件单独通过原确认函数n拒绝，区分“纯文本旧历史”和“确有程序回执”，不补造原案例。完整历史1次/4484、全隐藏2次/8781、typed 4次/18916均完成。回执存在能改善可检索性，但不保证模型选最短路径。
- combined组合“用户原话＋真实回执/正文定位＋计划完整循环＋程序文末来源”，3次/8785完成旧候选修改，n拒绝，程序文末附第1轮真实来源。它是一条集成观察，不代表单项收益可直接相加。

深层判断：同一AI消息目前混合模型建议、候选正文、程序追加回执；而正式计划还散落在system文本，动态状态JSON另列任务。删除或保留整条AI都不够精确。应按内容职责处理：近期用户条件、近期编辑对象、正式程序事实、待核对助手判断。旧格式保留兼容回读，不凭自然语言自动猜是否确认。

## 组合采用/恢复暴露的新问题与修订

另设隔离测试输入y：组合从旧候选保留第一项12分钟、第二项改两个例子8分钟，确认后修订1→2；再新进程发送：

> 请复述当前正式计划和read-001的活动进度与理解反馈；说明它与未采用的旧候选的关系。只查询，不修改任何记录。

初版所有状态保护检查通过，但回答说“当前没有已采用的正式计划，未显示current_plan字段”。真实请求里其实有新计划，只是以独立文本传入，任务JSON没有plan字段；正文标题又叫“候选学习计划”。模型猜了不存在的字段。此为内容恢复失败，不是状态保存失败。

### 唯一正式状态包（combined_v2）

测试侧改为从真实LearningState重新生成正式JSON，而不是从聊天文本合并字段；目标、完整计划、revision、任务及反馈视图放在同一入口，去掉另一个旧计划副本。分析笔记与材料另列，不冒充正式状态。关键代码：

```python
official = json.loads(app.build_learning_state_message(state).content)
official.update(
    learning_goal=state.learning_goal,
    plan_markdown=state.plan_markdown,
    context_revision=state.context_revision,
    plan_status="active",
)
```

active表示此真实状态中的当前计划，不由正文标题推断，也不写入原持久化schema。实际正式实现应显式传入状态/证据对象，不沿用实验从inbox私有字段取对象、解析原system字符串的接线方法。

没有加“这道题正确计划是……”的提示。同一个已采用快照、同一句查询：原流程正确；初版组合错误；v2复验正确识别20分钟正式计划、完成/理解不清楚及旧一个→新两个例子的关系。原流程1次/4792输入、v2两次/6360，不能称性能更优。
