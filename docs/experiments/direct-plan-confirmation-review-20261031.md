# 工具候选直接进入确认的方案（2026-10-31）

## 澄清与必要性

已核实上一轮工具方案实际落地，当前源码核心48项通过。当前START/END由PlanProposalInbox.render_reply程序生成，模型仅提交plan_markdown；不能声称仍要求模型生成计划标记。上一轮保留这段桥接是复用旧确认入口的迁移策略，不是新工具所必需。

本轮提出去掉新通道“结构化候选→标记文本→解析回候选”的往返。模型输入、工具参数和生成提示词保持现状，不增加模型、裁判或固定教学模板；提升的是程序契约直接性和可测试性，不承诺单靠这次内部调整提高模型内容质量。

## 数据通道

PlanProposalInbox保留pending原始参数，新增confirmation_plan（来源规范化后的待确认正文）与conflicted（冲突），每轮清空。prepare_delivery返回参数对象或None，不生成展示标记。执行校验通过后，出口规范化正文来源并填入confirmation_plan；展示单独渲染。外层以字段检测候选及冲突，新通道直接将正文交给_review_context_change。只有无工具交付时使用旧标记解析器，兼容旧计划/目标入口。

来源函数增加include_notice=True兼容参数；候选正文仍替换无效引用为未核实标识，但不将来源核验附注和来源列表写入计划。展示保留附注。这是展示选择，不改变证据判定。被sanitize_learning_action_reply隐藏的回复必须同步清空本轮submitted_plan，避免隐藏正文仍从数据通道进入确认。显式指定执行要求未满足仍不能开放confirmation_plan；与反馈混用的conflicted明确阻断两者，不依赖文本标记。

## 测试及边界

新通道沿用同一联合案例和自动v/y或v/n输入；测试将旧计划/目标解析器替换为“调用即失败”，仍须采用/拒绝、源保护、任务与反馈保留及跨进程恢复通过。新加3种正文布局可保留、下一轮字段清空、错误引用附注不进入计划、伪造程序回执导致展示隐藏时禁止交付等测试。

原工具16项测试更新为数据通道契约并增加4项至20项；联合9项增加2项至11项。旧文本入口采用/拒绝、混合操作、显式执行保护、来源及预算等回归保留。候选只在内存装载，共163项通过，2条pytest已导入插件断言重写提示；未修改业务源码、未做候选在线实验。子进程使用磁盘正式CLI恢复父进程候选写入的相同格式，证明恢复兼容，不声称子进程已执行未落地的新提交逻辑。落地后需在正式源码再次运行。

新测试依赖prepare_delivery及confirmation_plan，当前桥接源码未应用候选前预期不满足，不跳过或放宽断言。候选评测不证明教学效果，含错误引用的反例即使被测试脚本y采用也只验证程序契约，不判内容质量通过。

## 联动和落地
