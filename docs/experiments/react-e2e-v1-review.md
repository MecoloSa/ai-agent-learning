## 4. 已确认的问题与建议修正

### 4.1 agent：混淆两种不同分类（优先级高）

位置：第一天任务 1。

原计划列出“系统指令、工具定义、思考过程、历史记录、工具执行结果”，并把后三项直接归为动态消息历史。

原文第 20 页介绍的上下文组成是系统提示词、工具定义、用户消息、模型回复、工具执行结果。第 21 页消融表使用系统指令、工具定义、思考过程、历史记录、工具结果等实验维度。这两种划分服务于不同目的，不能直接等同。

建议改为：先用用户消息、模型回复、工具结果解释动态历史，再单独说明消融实验在哪些信息维度上做移除对照。不要把 reasoning 当成任何聊天 API 都必须独立提供的消息角色。

动态评估：人工检查或语义评审应确认计划能区分“消息结构”和“实验维度”；不能只匹配“五个组件”等关键词。

### 4.2 pipeline：消息轨迹验收与自己的示例矛盾（优先级高）

位置：第二天任务 3，“至少 3 轮完整的 user → assistant → tool 消息序列”。

同一计划前面的示例已经显示：用户在开始时提问，随后工具调用与结果交替，最后 assistant 给出答案。工具循环每一轮不需要新 user 消息，最终回答也不需要 tool 消息。

建议要求：画出至少两轮工具调用及一次最终回答，标明初始 user、assistant 的工具请求、对应 tool 结果、最终 assistant 答案，并标记每次模型调用看到的上下文范围。

动态评估：检查工具请求与返回的对应关系，以及最后能否正常退出，不以固定的角色三连序列作为每轮规则。

### 4.3 pipeline：固定假响应不能证明真实消融效果（优先级高）

位置：第二天任务 4 的模拟器、消融测试及测试 C。

预设模型一直返回相同 Action，可以测试重复保护或最大轮数是否生效。但是，如果输出已经固定，它不会因为 history 的变化而改变，因而不能证明“删除工具结果导致模型重复”。

另一个错误是“history 长度不增长（无工具结果追加）”：即使不追加工具结果，assistant 消息仍可能追加，所以总长度不增长并非必然。

建议将两类实验明确分开：

- 单元测试：用假模型验证正常退出、达到预算、重复调用受控。判定是退出原因、调用次数和消息配对，不是证明真实模型退化。
- 真实消融实验：固定任务与配置，对完整上下文、缺少可用反馈、裁剪历史分别做对照，记录完成率、重复调用率与退出原因；观察是否退化，不预先保证退化。

如果假模型确实根据传入 history 分支响应，可以验证上下文传递是否符合设计；仍不能替代真实模型实验。

动态评估：记录 `step`、工具名称与参数、结果状态、消息数量、退出原因。缺少工具结果应检查该结果是否进入下一轮输入，而不是断言所有历史停止增长。

### 4.4 agent：测试产出停留在设计，且混淆 Finish 与真实工具（优先级高）

位置：第二天任务 2 和最终验收清单。

计划要求三个测试方案、伪代码和修改说明，而案例强调终止条件测试。建议至少要求运行一个最小测试脚本或现有 pytest 用例，提交断言结果和退出原因。

Hello-Agents 第 93 页先识别文本 `Finish[...]` 并直接返回答案，再处理普通工具查询。因此该实现里的 Finish 是完成标记，不应不加区分地称为实际注册工具。当前项目的结构化工具调用流程也不应直接套用这套文本解析实现。

“复现消融实验：说出五组实验的缺失组件和对应后果”实际是解释实验，不是复现实验；只有执行对照、保留结果才适合称复现。

动态评估：分别统计“写出测试方案”“测试已执行”“断言通过”，不要将三者统一记为完成。

### 4.5 两份计划：限定失败结论，保护工具协议与思维链边界

两份计划都把缺少结果写成必然反复调用甚至无限循环。建议使用“书中实验观察到”“可能增加重复风险”，并保留轮数与重复调用保护。

agent 的消融建议是删掉 Observation 追加。这适用于所引用的文本 ReAct 教学实现，不能直接照搬到当前结构化 Function Calling 消息列表：删掉与 tool_calls 对应的 tool 返回可能先造成消息协议校验错误，而不是预想的模型循环。

两份计划引用了书中的 Thought 或 reasoning 示例。这不自动构成要求泄露私有思维链，但应明确：只记录可观察的工具请求、结果状态、简短公开计划和终止原因；不要求提取、存储或还原模型内部推理。

### 4.6 agent：时长和数量不一致（优先级中）

- 第一天任务 1 标注 2.5 小时，步骤是 30+45+45 分钟，合计 2 小时。
- 第二天任务 2 标注 2.5 小时，步骤是 45+45+60+30 分钟，合计 3 小时。
- “学习四种终止条件”实际列出正常、最大轮数、错误熔断三类，第四项只是重复解释 max_steps。

按任务标题合计 11 小时，按步骤也合计 11 小时，但每日分配不同。这两天对初学者是否可行，需要用户每日时间预算，不能仅凭天数判断。

动态评估：时间汇总与数量一致性适合用规则检查；估时应标明“计划设计”，不伪装成资料规定。

## 6. 下一步具体做什么

### 第一步：把本报告变成固定验收依据

暂时保留 v1 原始 JSONL 不动。给这个案例建立独立质量检查清单，至少覆盖：上下文分类、反馈闭环、消息配对、终止测试可执行、引用支持、私有思维链边界。

不要直接往案例 JSONL 添加任意字段：当前 `EvalCase(**json.loads(line))` 只接受四个已定义字段，额外字段会报错。初期可用独立评审文件保存判定；之后再同步扩展案例结构与加载测试。

预期结果：不再只有“两个 success=true”，而能说明具体哪些要求达标、哪些不达标。

### 第二步：局部补强计划生成约束，而非重写架构

候选修改位置：`src/ai_agent/agents.py` 的 `create_study_plan()`，现有“最终计划必须遵守”规则之后。

拟补充约束：区分消息组成与消融维度；不要求每轮新增 user；实践任务提交可运行测试及断言；假模型只用于控制逻辑验证；书中观察不泛化为必然；时间合计一致；禁止把文本 Finish 与注册工具混同。

当前已有“教学设计必须标记”和“不得编造证据”规则，但 v1 仍出现问题，说明只写规则还不够，需要输出验收反馈。

本报告不直接改代码。真正实施时应给出该位置局部修改前后片段，并补测试；提示词改善也不能保证错误消失。

### 第三步：补评测判定与记录

候选修改位置：`src/ai_agent/evaluation/runner.py` 的 `RunRecord` 与 `run_case()`；配套 `tests/test_evaluation_runner.py`。

保留运行成功字段，另设质量判定，不把“非空输出”改名包装成质量成功。先增加可确定的规则检查，再对概念准确性和引用支持度进行人工抽检；之后才考虑 LLM-as-Judge（用另一个模型按固定标准评审）。

建议后续记录模型与关键配置、运行时间、代码版本、token/工具调用统计和终止原因。概念判定不能仅靠关键词，未经人工校准的模型评分也不能当作金标准。

测试至少覆盖：非空但概念错误的计划仍是运行成功、质量不合格；空计划；调用异常；缺少引用；格式合规但引用不支持内容。现有 runner 两个测试仅覆盖基本成功记录与异常记录。

### 第四步：生成 v2，再按同一标准比较

完成上述小改动并通过相关测试后，再运行真实端到端评测。此步骤涉及实际模型调用，不属于本次已执行内容。

PowerShell 命令在项目根目录执行：

```powershell
uv run pytest tests/test_evaluation_runner.py tests/test_agent_loop.py

uv run python -m ai_agent.evaluation.runner `
  --cases tests/fixtures/evaluation/end_to_end_smoke.jsonl `
  --output .evaluation-results/react-e2e-v2.jsonl `
  --modes pipeline agent
```

前一条用假模型检查程序行为，后一条调用真实学习助手，并将两种模式的结果各保存一行。当前 runner 已包含控制台摘要，不再是早先完全静默的版本。

输出路径必须使用新的版本号：`write_record()` 实际整文件覆盖，并不是其 docstring 所写的追加。重复实验也要用不同文件名保留原始结果。

预期结果：v2 的两条记录均被保存；随后用本报告的同一清单检查已确认问题是否减少。新记录仍然 `success=true`，本身不证明修复有效。

进一步比较可扩大到 5–10 个有明确验收标准的案例，并交替模式顺序、做多次重复。分别汇报质量、完成率、延迟、token 和费用，不将引用数量或单次耗时作为最终排名依据。
