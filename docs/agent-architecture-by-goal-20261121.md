# 不同任务目标下的 Agent 架构选择

整理日期：2026-11-21。本文结合官方实现说明、论文和本项目实验。产品文档用来说明用户可观察的功能。只有公开实现或技术报告披露的部分，才用来判断内部架构。

## 先确定要交付什么

| 目标 | 合适的执行方式 | 执行时保留的上下文 | 完成条件 |
|---|---|---|---|
| 根据已知资料解释一个概念 | 一个模型读取或检索后作答 | 本轮问题、所需原文、用户指定范围 | 解释准确，用户能回到原文核对 |
| 并行查阅多份独立资料 | 协调者按证据需求分派，再集中综合 | 每路的目标与证据、各路交付物和出处 | 各边都取证，说明共同点、差异和适用范围 |
| 后一步需要前一步的结果 | 显式依赖，具备上游产物后再开始 | 上游核对出的值、出处及与当前问题相关的原文 | 后续工具调用确实使用上游产物，可追踪到新证据 |
| 面向学生辅导和练习 | 以多轮互动为主，视情况调用资料工具 | 当前目标、学生尝试、反馈、需要继续解释的资料 | 回应符合当前教学意图，提示、练习和答案适时出现 |
| 修改有持久状态的计划或执行业务操作 | 程序管理状态与确认，模型承担解释或生成候选 | 正式状态、候选内容、用户确认及执行回执 | 确认后才写入，失败可说明，执行结果可验证 |
| 长时软件工程与研究 | 工具循环、持久事件记录、阶段产物与按需恢复 | 任务和近期动作、仍然有效的事实、可回读的原始记录 | 可观察的成果达到要求，例如测试结果、文件或有据报告 |

Anthropic 将固定流程和自主 Agent 都看作可选构件，并建议按照实际需求逐步增加复杂度。OpenAI Agents SDK 区分由程序编排和由模型编排，也区分把子智能体作为工具与把对话控制权交给专家。阅读助手由统一的用户交互模型组织解释，通常适合调用子智能体取得证据后收回产物。只有用户交互本身要换成特定专家的角色时，才需要考虑控制权交接。 [Anthropic 工作流与 Agent](https://www.anthropic.com/research/building-effective-agents) · [OpenAI Agents SDK 编排](https://openai.github.io/openai-agents-python/multi_agent/)

## 公开方案及其取舍

### 开放研究与简单取证

Anthropic Research 采用协调者与研究子智能体。协调者选择调查方向，子智能体各自搜索、调整查询并压缩发现，最终结合证据形成报告。它适合资料多且搜索方向相互独立的问题。其公开经验也指出，多 Agent 会增加 token 消耗，需要以质量和任务完成度衡量收益。项目中两本教材分别核对可以并行。指定一页解释一句话时，并行研究的投入通常缺少相应的收益。 [Anthropic Research 工程说明](https://www.anthropic.com/research/multi-agent-research-system)

LangGraph 的 Orchestrator–Worker 示例通过 `Send` 动态分派任务，每个 worker 得到自己的输入，再将结果归并。当前项目的阅读委派实验也采用协调者与子任务，另由就绪队列处理前置依赖。这样可以表达“第 41 页取到 ID 后，再按 ID 定位第 40 页”。检索与比较阶段的分界可用真实工具轨迹来验收。 [LangGraph 官方编排示例](https://docs.langchain.com/oss/python/langgraph/workflows-agents#orchestrator-worker) · [项目就绪队列](../tests/helpers/reading_dependency.py)

### 有资料依据的问答与教学交互

Gemini Notebook 的官方帮助说明，用户可以指定资料，回答带有可打开的来源引用，也能选择学习引导风格。这说明资料核验和教学表达可以在同一产品中分别控制。公开页面提供的是产品行为，内部如何路由、分块和压缩没有在这里披露。项目可借鉴的界面能力是让用户回到出处，尤其要保留物理页、印刷页和 PDF 显示标签的区别。 [Gemini Notebook 对话帮助](https://support.google.com/notebooklm/answer/16179559)

LearnLM 把教学效果作为模型行为单独训练和评估。受监督的 Eedi 课堂研究也使用了具体教学对话，观察提示和后续学习任务的表现。这些结果不能直接转用为本项目的效果分数。它们提供了验收上的区别：用户要一道练习且不给答案时，需要评估答题范围和是否泄露答案。用户想澄清误解时，需要评估解释是否回应了学生的具体理解。取证结果正确仍可能伴随教学交付偏差。 [LearnLM 技术报告](https://arxiv.org/abs/2412.16429) · [LearnLM 与 Eedi 课堂实验](https://arxiv.org/abs/2512.23633)

### 长时执行与上下文整理

Deep Agents 默认让独立子智能体接收委派，其工具和权限可继承或按角色配置。上下文压力上升后，可以把大工具结果移到存储，保留回读引用，并在需要时摘要旧历史。项目中全量工具回执的价值在于可追溯，短任务可以直接使用。长任务可以只整理发送视图，并保留正在对照的原文。 [Deep Agents 子智能体](https://docs.langchain.com/oss/python/deepagents/subagents) · [Deep Agents 上下文工程](https://docs.langchain.com/oss/python/deepagents/context-engineering)

OpenHands 将会话事件和用于模型推理的视图分离，Condenser 在保留完整事件记录的基础上整理旧历史。软件工程任务需要能回看真实命令、文件差异和测试结果。对学习助手，相应的事实是资料原文、引用位置、用户更正和正式学习状态。摘要可以记录进度和待查问题，逐字引用和协议细节仍应以原文为依据。 [OpenHands SDK 论文](https://proceedings.mlsys.org/paper_files/paper/2026/file/8ae9cf363ea625161f885b798c1f1f78-Paper-Conference.pdf) · [Condenser 实现说明](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/README.md)

### 授权与有副作用的工作

Claude Code 的子智能体可以配置工具白名单、权限模式和条件检查。Deep Agents 也把工具配置与文件权限作为独立配置项。应用到学习助手时，用户允许的文件或明确的页码属于读取边界。规划给出的优先文件属于分工。正式计划、任务状态等写入，则继续通过独立的确认流程。这个设计让模型可以补查用户已允许的资料，同时由程序保证读取与写入的权限安排。 [Claude Code 子智能体权限](https://code.claude.com/docs/en/sub-agents#control-subagent-capabilities) · [Deep Agents 子智能体配置](https://docs.langchain.com/oss/python/deepagents/subagents#custom-subagents)

## 对本项目的设计建议

1. 首先保留简单路径。已给出页码或问题只需要少量资料时，让同一模型完成理解与解释。若有两份证据可以各自核对，把任务按独立贡献拆分。多个模型使用同一批原文重复综合时，应比较它们实际增加了什么。
2. 明确传递下游所需的中间结果。用两个调用 ID 的例子，交接对象包括原样 ID、各自对应的工具、返回端页码及原文。下游拿这些内容查请求端。只有下游确实依赖结果时，才在图中表达等待关系。
3. 把长期记录、当前模型视图与正式状态分别对待。完整工具轨迹用于审计，当前视图可以去重与整理，正式计划由程序负责写入。对于仍在核验的原文，为模型保留同时对照的能力。其他旧材料保留可回读入口。
4. 把任务质量与资源指标同时记录。重点记录覆盖了什么、引用可否核对、是否遵守练习范围、重复回查多少次、累计输入 token 和端到端耗时。整理阶段自己用的模型调用也要纳入成本。

## 下一轮实验的判定方式

| 场景 | 初始材料与处理方式 | 通过标准 |
|---|---|---|
| 明确核验两页 | 固定相同原文和读取序列；保留当前两页，其余旧证据保留位置 | 关键结论与原文一致；核对页同时可见；请求往返不反复 |
| 广泛资料综合 | 用固定真实教材节选；比较完整原文、先分批做笔记再汇总 | 覆盖所有提问维度；回读入口正确；笔记与汇总合计成本有收益 |
| 早期证据重新变重要 | 把早读的页降为可回读，再提出必须对照该页的任务 | 能重新取得原文并正确解释；回查一次后可以同时比较 |
| 规划漏派资料 | 固定同一条只建议 A 书的委派，用户许可还包括 B 书指定页 | Flash 可补读 B 的授权页；相邻未授权页仍被拒绝 |

本次在线上下文对照采用真实 PDF、固定证据和固定读取序列，以测试发送给模型的内容。活跃页由评测提供。这与让模型自行识别关键证据、自由安排查资料的完整流程不同。下一轮若在真实任务上无法自动判断哪些证据仍重要，应先接入确定性的去重及上游证据交接。

## 本项目对照结果

- **漏派资料。** 固定同一条只分派第一本的委派，要求核对第一本物理第 36 页和第二本第 85 页。旧工具拒绝第二本，最终只能交付第一本。共享用户授权范围后，模型实际取得并使用两页。程序回归另外验证第 86 页和未授权文件仍被拒绝。
- **局部对照。** 同一批 13 页节选，比较工具反馈的作用和两个调用 ID 的配对。首轮保留第 20、41 页和近期回执，两个候选都一次完成，输入各 5942 token；完整回执两次都尝试回查不在存档中的证据，累计输入各约 2.64 万 token。该差异与额外调用有关，不能推广为普遍节省比例。
- **早期证据回查。** 要求回到第 36 页的定义并核对第 41 页。首轮只保留第 41 页和近期回执时，两次都取回了第 36 页，两次累计输入分别为 11151、21924 token。第二次出现三个无法解析的证据引用。保留完整正文两次均为 13153 输入 token。回查工具的标识设计会直接影响整理能否节省成本。
- **回查接口的迭代。** 给已保存的证据增加本轮专用短编号，两次均取回第 36 页，累计输入为 12376、8429 token，第一轮仍有两次无效引用。随后试按物理页回查同一批保存结果，累计输入为 15751、14809 token，有额外选页。短编号在这个案例里值得保留为候选，但仍须校验是否属于当前目录。对当前请求已明确点名的页，应在第一轮保留原文，省掉必要的回查。
- **广泛资料讲解。** 要求讲清工具声明、调用、执行回填、继续推理及缺少反馈的后果。完整节选一次交付约 1.30 万输入 token。分三批生成笔记再汇总，模型又回查五页正文，合计约 2.98 万输入 token。当前节选规模适合直接使用原文；分段笔记的收益需在更长资料上验证。

今后的第一版应保留正在对照的原文、按压力整理较早回执，并提供好引用的回查入口。内部证据身份仍使用可追踪的稳定 ID，短编号只用于本轮递交给模型的目录。对不具备明确证据锚点的主题讲解，继续保留完整回执作为基线。上下文回放初次把历史读页工具名用于只开放证据回查的请求，部分模型随历史工具名发起调用，导致测试适配器错误。修正为历史调用与当前绑定使用同一接口后，两组一并重测。实验用例与结果保存在本地 `.evaluation-results/report-priority-lab`。
