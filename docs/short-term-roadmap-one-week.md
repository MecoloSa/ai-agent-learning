# 短期计划：验证反馈计划质量，补齐记忆可靠性

> 更新日期：2026-10-23。实施窗口：未来两周，约每天2—3小时；第一周完成评测基线，第二周完成最小改进与对照。文件名保留以兼容已有链接。
> 本文替换旧路线；历史实现与提案见 [实现记录](implementation-history-through-20261023.md)。以下新增模块和字段均为计划，不表示已经实现。

## 1. 本轮目标与范围

把“反馈 → 候选 → 用户确认 → 保存恢复”的控制闭环，推进到“能发现约束冲突、展示修改依据、比较记忆策略”的质量闭环。

本轮交付：

1. 一套固定的反馈计划评测集和可重复运行器，分开报告控制、内容、证据和成本。
2. 一份候选质量诊断，用户确认前可查看；不把未发现问题等同于质量通过。
3. 滚动摘要与失败保护，以及full/window/summary同题对照报告。

保留pipeline/agent、legacy/langgraph、local/mcp与检索开关。默认路径不随评测结果自动切换。本轮不引入新Agent、自动修订循环、向量记忆库或存档整体迁移。

## 2. 已完成基线：不重复开发

| 能力 | 当前状态 | 本轮处理 |
| --- | --- | --- |
| 工具执行 | 绑定目录、预算、同参保护、执行核验、有界参数错误反馈 | 保留回归，评价纠正效果而非再建循环 |
| RAG | 向量/BM25、RRF、聊天/专用重排、精确读取、回退与实验入口 | 保持配置固定，评测具体论断支持 |
| 反馈与任务 | 自然语言候选、确认、创建/取消、正式反馈、更正链、历史查询 | 作为评测真实业务入口 |
| 状态与恢复 | current/历史快照、聊天策略持久化、资料指纹、恢复问答 | 覆盖独立进程恢复，不重新建设 |
| LangGraph | 三节点、轨迹、SQLite检查点及受限失败规划续跑 | 本轮不迁移交互循环 |
| MCP | 按行读取stdio试点、可选接线、连接管理与对照 | 试点收尾，不扩写状态能力 |
| 质量检查 | 非空计划、字段与引用标记检查 | 增加独立内容诊断，不继续堆排版正则 |

2026-10-23复核全套离线测试：1001通过、1跳过。该结果是当日基线，不是未来运行保证，也不证明模型回答准确。

## 3. 第一周：先建立可量化基线

### 第1天：定义评测案例和判定契约

新增位置：

- tests/fixtures/evaluation/feedback_plan_cases.jsonl：初始状态、对话脚本、输入依据和预期结果。
- tests/fixtures/evaluation/feedback_plan/：小型技术与非技术资料、初始计划与状态。
- tests/fixtures/evaluation/README.md：案例字段、隐私范围、开发集/留出集使用说明。

先做12个案例，8个开发、4个留出。留出只表示不用于本轮调参；一旦据此修改方案就记录为已使用，后续补新案例，不反复称其独立留出。

| 编号 | 输入变化 | 必须检查 |
| --- | --- | --- |
| 01 | 时间从60分钟减至30分钟 | 分项合计与总上限一致 |
| 02 | 每项时间给区间 | 合计区间上界是否超过预算 |
| 03 | 只阅读、口述 | 不残留绘图、编码等冲突活动 |
| 04 | 阅读完成但不理解 | 保留完成状态，活动针对具体困难 |
| 05 | 只讨论 | 无pending写入、无计划修订 |
| 06 | 预览后拒绝 | 业务字段不变，回执说明实际拒绝 |
| 07 | 确认采用 | 修订变化正确，初始计划和任务反馈保留 |
| 08 | 更正多条件反馈 | 最新确认正文完整，来源与更正链不丢失 |
| 09 | 多个登记任务 | 只影响指定对象，不把任务表当计划全文 |
| 10 | 跨日或旧版本反馈 | 明确来源时间，不擅自认定仍适用或失效 |
| 11 | 证据缺失/截断 | 说明缺口，不编造支持依据 |
| 12 | 保存后新进程恢复 | 当前计划、反馈、历史候选和任务状态不混淆 |

至少包含一份非技术资料和一组“同一资料、不同目标”。案例中的分钟数只是测试输入，不能写成产品固定规则。

每项判定保存expected、实际观察、证据位置和人工标签。无依据时允许unknown；不能用关键词缺失直接判定语义违规。

完成标志：无需在线调用即可加载全部案例、校验ID及字段，并能清楚说明每项测试证明什么。

### 第2—3天：接通可重复评测运行器

新增src/ai_agent/evaluation/feedback_plan_runner.py，复用main.py中的实际交互、确认、保存和恢复路径。CLI输入输出可通过适配层驱动；不能复制另一套业务提交逻辑，也不能由测试脚本直接改状态冒充模型完成。

参考现有evaluation/runner.py、interactive_runner.py和tests/test_feedback_plan_loop.py，但给新案例定义独立加载契约，不将多轮字段直接塞入现有EvalCase导致不兼容。

运行器需要：

1. 每案例独立临时目录、current文件和运行ID，不读写个人存档。
2. 显式区分离线替身模式与在线模式；默认不请求模型。
3. 在线模式记录实际模型、代码提交及dirty标记、提示词/案例/资料指纹和关键配置。
4. 记录真实执行、状态前后差异、候选、确认结果及结构化判定；公开摘要不含正文或敏感路径。
5. 新文件保存实验，拒绝覆盖已有结果；异常也保存已收集的诊断。
6. 新进程恢复作为单独验收，不能用同进程重新构造对象代替。

建议结果字段（计划中的契约）：run_id、case_id、execution_mode、control_checks、quality_checks、evidence_checks、usage、latency、error、config_snapshot。判定维度各自计数，不能将所有检查项的平均值当案例成功率。

正常路径、拒绝、参数失败、保存失败、恢复失败都要有测试。保存失败应明确“内存生效但未落盘”，不误判成成功恢复。

完成标志：离线跑通全套脚本；至少一次在线开发集运行能保留逐例结果，控制通过与语义失败分开显示。

### 第4天：建立人工判定与Judge的对应关系

修改evaluation/review.py或新增feedback_plan_review.py，给反馈修订提供适合的评审上下文：旧计划、新候选、已确认反馈、原文证据与实际修改范围。不要只把新计划交给评审者。

判定分层：

- 程序检查：状态是否误写、修订号、确认授权、可明确读取的数值合计。
- 人工/独立模型：活动与困难是否对应、方式冲突、任务量是否合理、具体论断是否受支持。
- 不可确认：估时缺失、用户条件含糊、资料不足，保存null/unknown及原因。

先人工标注开发案例，再用现有Judge校准方法比较。人工标签不发给模型；报告错放、误拒、未知和评审失败。生成和评审分开调用，优先尝试不同模型；相同模型分角色不代表偏差独立。

完成标志：固定一份判定标准，能够解释为什么“格式合规、状态正确”的候选仍会内容失败。

### 第5—7天：基线运行、失败归类与文档

开发案例在线至少重复两次；预算不足则缩小案例覆盖并如实说明。交替条件/顺序，不同时改变模型、检索阈值、工具预算和记忆策略。

统计：控制边界违规数、约束满足计数、证据支持计数、未知比例、工具纠正结果、输入输出token、额外重排/摘要请求和耗时。缺失usage记null，不作0；小样本报告逐例值，不宣称稳定p95或显著提升。

新增docs/experiments/feedback-plan-baseline-日期.md，记录输入版本、配置、成功与失败、指标分母、开销与局限。同步docs/demo-and-acceptance.md与README，避免把自动输入y写成质量认可。

第一周验收：12个案例可加载；实际入口回放可复现；至少识别并保留一个“控制正确、语义不合格”的反例。若运行器仍不可信，不开始自动修订或大规模结构改造。

## 4. 第二周：基于失败做最小改进

### 第8—9天：在确认前展示独立质量诊断

修改位置：main.py::_review_context_change()，候选生成后、用户确认前。新增learning/plan_quality.py或runtime/plan_quality.py，保持与现有plan_validation.py排版检查职责分离。

第一版只读检查，不自动修改候选、不增加重试、不新增存档版本。建议报告采用：violated、no_detected_violation、unknown，逐项给出可见依据。明确“没发现问题”不等于“已通过全部质量验证”。

优先实现明确可确定的时间合计检查；未识别单位、范围或任务结构时返回unknown。活动方式与困难匹配先走评审，不以搜索“画图”等词作为通用语义判定。

确认界面提供原候选、诊断和修改概述；用户仍可预览、确认或拒绝。内容质量问题与硬性权限/状态校验分开，诊断不能授权写入。

测试：数值超限、区间上界超限、估时缺失、不同布局、提示不修改候选、拒绝不改状态。对开发集比较误报与漏报，不因误报而删除所有检查。

完成标志：用户能看到具体疑点；已知时间冲突可被诊断；旧确认与保存测试保持通过。

### 第10—11天：修复短期记忆机制

修改persistence/memory.py中的get_messages_for_llm()和_maybe_compress()，更新tests/test_memory.py及会话存取相关测试。

实施顺序：

1. window按现有“消息数上限”保留完整问答，不静默改成轮数；覆盖奇数窗口和未回答用户消息。
2. 摘要输入同时包含旧摘要和新增历史，以新摘要替代旧摘要。
3. 触发阈值和摘要输出预算分开；检查空、异常类型与超长输出，不直接截断否定或限制条件。
4. 所有校验通过后再丢弃被压缩历史；失败保留原历史和摘要，不中断已经得到的回答。
5. 保留反馈/确认的可信来源，历史摘要仅作背景，不提升为新指令或最新业务事实。
6. 与现有MemorySnapshot兼容；确需持久化新增配置时先设计默认值与旧版本读取测试，不顺手升级全套存档。

明确局限：成功摘要有上限不等于整个请求有硬token上限；摘要失败保留历史会继续占空间。固定system、工具schema、状态和证据需分别观察。

完成标志：第二次压缩看得到第一次摘要；失败不丢消息；最近完整问答保留；存档恢复后行为一致。

### 第12—14天：三策略对照与阶段收尾

新增tests/fixtures/evaluation/memory_cases.jsonl和evaluation/memory_eval.py，复用已建立的多轮驱动能力而非另写提交逻辑。

用10个脚本比较full/window/summary：早期限制、指代、更正、目标改变、确认/拒绝历史、跨日、恢复、来源查询和无依据拒答。固定其他配置，初步各重复两次；在线成本按实际预算控制。

报告最新约束使用、历史对象混淆、无依据回忆、来源查询、token和延迟；摘要的额外请求全部计入。不要只统计summary长度或“成功返回”。

将改动后的开发结果与基线配对，再执行未用于调参的案例。收益不足时保留原默认策略，局部回退不影响反馈来源和确认边界。

第二周验收：候选诊断和记忆补丁分别有独立验证；形成一份改进前后报告，公开摘要不暴露原始存档。

## 5. 统一测试与回退方法

受影响测试先通过，再运行全套。示例从项目根执行：

```powershell
uv run pytest tests/test_memory.py tests/test_plan_validation.py tests/test_feedback_plan_loop.py tests/test_plan_confirmation_preview.py --basetemp tmp/short-roadmap-targeted
uv run pytest --basetemp tmp/short-roadmap-full
```

新增模块完成后，将对应测试加入定向命令。--basetemp必须使用本轮独立、可清理的测试目录，不能指定资料或用户存档目录。在线运行命令在新runner落地后写入其--help与README；本文件不虚构尚不存在的可运行命令。

每步独立提交，先写失败案例再改相关逻辑。出现未确认写状态、拒绝仍改变计划、跨存档污染、恢复来源被覆盖等情况立即停止扩展并回退该步。模型内容无改善时先检查失败归因，不扩大预算掩盖问题。

## 6. 本轮后续入口

时间不足时依次保留：可信评测 → 候选诊断 → 摘要修复 → 对照报告。结构化计划、交互LangGraph、索引配置版本和长期记忆见[长期路线](long-term-roadmap.md)，不要求在两周内同时落地。

本轮面试证据：能演示一个真实失败，解释程序检查与语义评审的分工，用同题结果说明修复收益、额外成本和仍存在的局限。
