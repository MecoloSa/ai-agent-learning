# 学习Agent提示词设计原则

整理日期：2026-11-02。用于学习与方案评审，不是新增运行提示词。不存在适用于所有Agent的统一字数、示例数或规则数标准；以下区分官方指导与本项目工程判断。当前模型为Qwen/DeepSeek，跨模型效果需验证。

## 1. 每句话先确定职责和归属

2026-11-04 补充：先追踪实际发送边界，再判断一句话是否属于提示词。普通函数的注释、docstring不会自动发给模型；但`@tool`或`StructuredTool.from_function`可能把函数docstring作为工具描述发送，必须检查最终schema。系统消息中不放迁移过程、接口兼容或维护者说明；动态消息保留真实状态和理解字段所必需的语义。程序已经接管的操作结果及引用展示，应替换原来的模型职责说明，不再叠加近义要求。

一段说明应回答：它会改变什么决策，模型缺少它会不知道什么？系统提示保存稳定职责、证据与授权边界；工具描述说明用途、参数语义和返回含义；动态消息提供本轮事实；程序负责权限、预算、确认与保存。不要在三个位置重复讲同一工具的完整使用方法。

OpenAI官方介绍消息角色、上下文组织及持续评测，提醒不同模型甚至快照可能需要不同提示方式：[Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)。这是组织原则，不是本项目改变role后自动安全或效果更好的保证。

## 2. 简洁不等于省略关键参数语义

类型和范围能写进schema时由schema表达；行号从1开始、包含两端、source_index仅属于本轮来源表等语义仍需说明一次。不要让模型猜测这些契约。root_dir、存档路径、当前状态等程序已知值由程序绑定，不要求模型复制。

函数名称、参数说明、输出意义、把已知参数交由代码处理、控制初始工具面，是OpenAI官方工具设计建议：[Function calling](https://developers.openai.com/api/docs/guides/function-calling)。并非所有参数解释都是冗余，也不是工具越少越好。

## 3. 限制由程序执行，提示只提供决策所需信息

不要让模型记账、计算重试次数或凭口头确认写入。初始系统通常不需讲重试内部算法和异常处理细节。失败发生时提供code/retryable/必要字段位置即可。是否告知剩余总预算属于待测策略：完全不告知可能导致探索用尽预算；每轮长表又有重复成本。优先比较当前方式、仅临近耗尽提示、完全隐藏三种方式，程序边界保持相同。

本条预算通知取舍是本项目假设，不是官方统一标准。

## 4. 给目标与证据，不替模型固化合理路径

允许直接读取、检索定位、批量互补查询或必要澄清，不无条件要求先list。活动形式服从用户和资料，不固定每日任务数，不把阅读资料默认变成编程任务。保留用户明确范围与预算，允许模型提出教学建议，并区分建议与原文事实。

Anthropic强调过细且脆弱的行为逻辑和过于模糊的指导都存在问题，工具职责应清楚、避免歧义：[Effective context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)。不要把成熟项目的整段提示照搬到本项目。

## 5. 异常处理按需出现，不把故障手册放在每次请求里

正常路径只提供稳定契约。错误时返回可操作诊断；只有实际缺少提议、发生空响应或执行未满足要求时才注入纠正消息。不要为了字数删除纠错能力，也不在普通请求中预演所有失败分支。

## 6. 数据与指令明确分开

原文、旧聊天、摘要和程序状态都是数据，不因出现在system或JSON中就自动可信。稳定规则和动态资料尽量分开，原文中的命令不能升级为授权。状态、来源、候选、已确认、已落盘分别表达。role调整是结构改造，需联动恢复、摘要和状态更新测试。

## 7. 生成、抽取、重排、评审采用不同标准

自由问答允许多种合理表达；抽取器必须解释领域枚举与未知值；重排器需稳定输出可解析索引；裁判要保留固定评分口径。不能用“给模型空间”为由删除评审标准，再把评分变化当生成质量提升。

## 8. 不把所有问题都归因于提示词

先检查资料是否取得、是否被预算挤掉、状态是否最新、工具接口是否清楚、模型能力及服务响应是否正常。同类失败重复时优先定位职责和程序契约，不追加一串近义禁令。

## 9. 上下文整理与原始记录分开

工具轨迹保留供审计；模型请求可以使用新构建的视图。整理时保留调用/回执配对、未解决错误、必要原文和回查入口，不能机械删除最早若干消息。工具调用的参数同样可能很长，不能只统计ToolMessage正文。

Deep Agents的摘要中间件保留完整历史到后端，并在模型请求中应用摘要视图；还支持保留近期窗口及旧参数整理。它同时含截断与失败恢复取舍，不能原样照搬：[源码](https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/middleware/summarization.py)。OpenHands的Condenser/View接口要求只读输入视图，新建整理结果，并在摘要时照顾事件原子边界：[接口](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/base.py)、[摘要策略](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/llm_summarizing_condenser.py)。这里借鉴的是职责边界，不是搬用框架。

## 10. 修改须可比较、可撤回

固定模型、输入、资料、状态及预算，区分指令字数、实际请求token、费用和任务质量。开发与留出任务分开；先验证不会误写或丢证据，再做少量在线对照。允许没有收益的结论，不重复刷到有利结果。

## 写一段提示前的自检

1. 这是长期职责、工具契约、本轮事实，还是程序内部实现？
2. 是否已经在工具schema、描述或另一条消息里表达？
3. 没有它，模型真的无法正确理解任务或参数吗？
4. 能否改成明确工具、程序绑定或实际失败回执？
5. 是否限制了本可合理选择的路径或教学方式？
6. 准备用什么实际输入验证，什么结果会使我撤回修改？

## 阅读顺序

先读OpenAI的消息组织与工具设计，再读Anthropic的上下文讨论，最后看Deep Agents/OpenHands如何将原始记录与请求视图区分。框架源码链接指向阅读当日main，后续实现可能变化；本项目审计结论单独保存在prompt-and-context-audit-20261102.md。
