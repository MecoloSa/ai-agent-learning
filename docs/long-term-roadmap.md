# 长期路线：从可恢复的学习助手到可验证的Agent工程作品

> 更新日期：2026-10-23。面向2027年Agent工程相关实习。
> 以里程碑验收推进，建议窗口为未来3—6个月；时间仅用于安排投入，不能代替完成标准。
> 本文替换旧路线，历史逐轮方案见[实现记录](implementation-history-through-20261023.md)。新增模块、字段与开关均为规划。

## 1. 产品目标与推进原则

围绕一个可解释的场景持续迭代：资料提供依据 → 生成学习计划 → 用户反馈 → 有限调整 → 用户确认 → 保存并继续学习。

当前系统已有工具闭环、混合检索与重排、三种聊天记忆及恢复、反馈更正和查询、三节点LangGraph与SQLite失败续跑、MCP只读试点和多类评测。下一步重点是内容质量、记忆可靠性与可比较的工程证据，不重新建设已完成机制。

保留pipeline作为主要流程对照、agent作为自主工具路径；legacy与langgraph、local与mcp、检索策略分别控制不同变量。固定流程不表示模型输出确定；检查点恢复也不表示已完成节点内容正确。

每阶段遵循：固定失败输入 → 明确验收 → 最小修改 → 离线回归 → 小规模在线对照 → 记录边界。后阶段不以更换框架或增加Agent数量作为成功标准。

## 2. 能力现状与目标差距

| 岗位能力 | 当前基础 | 下一阶段应形成的证据 |
| --- | --- | --- |
| 工具调用 | schema、权限、执行核验、预算、错误反馈 | 选择正确率、错误纠正率、拒绝与终止轨迹 |
| Memory | 持久聊天、摘要、反馈更正链、历史工具 | 更新/时序/拒答评测，跨会话相关记忆与来源 |
| Planning & Execution | 反馈候选、独立确认、保存恢复 | 约束验证、稳定任务对应、局部补丁与失败恢复 |
| RAG | 稠密/稀疏、融合、重排、引用 | 索引配置版本、证据充分性、引用支持与成本对照 |
| LangGraph | 初始三节点、观察与受限续跑 | 一个有业务收益的交互子流程及恢复实验 |
| MCP | stdio只读试点和工具层对照 | 保留稳定边界，按真实需求才扩资源/传输 |
| 多Agent | 分析与规划职责分离 | 生成/独立评审对照，必要时Supervisor实验 |
| 评测与发布 | 测试、检索/Judge/交互实验 | 固定留出集、统一运行清单、回归入口与演示 |

本项目为人提供学习活动，不自动完成用户学习；任务完成、自报理解和客观测验依据必须始终分开。

## 3. 阶段A：质量基线与短期记忆可靠性（第1—2周）

执行[短期计划](short-term-roadmap-one-week.md)。交付反馈计划案例、实际入口运行器、候选诊断、滚动摘要与三策略实验。

退出条件：控制与语义质量分开统计；能复现并解释已知冲突；拒绝不写状态；摘要失败不丢历史；有成本和回退记录。

未通过时不启动自动优化循环，不用增加提示词示例替代评测。

## 4. 阶段B：结构化修订与验证（第3—6周）

### 目标

让用户看到“改了哪些任务、依据哪些反馈、还有哪些约束未验证”，并让程序能够核对明确的数值与任务关系。

### 实施顺序与文件

1. 新增learning/plan_candidate.py：仅为反馈修订定义候选结构，含稳定task_id、活动、估时或区间、完成标志、引用、修改理由及来源反馈ID。先保留现有Markdown路径作为对照。
2. 新增learning/plan_revision.py：表达增加/修改/移除等有限补丁；移除安排不等于删除学习历史。前置条件含基准修订号，禁止候选过期后直接提交。
3. 复用learning/learning_state.py与现有任务ID，明确登记任务和计划任务的关联；无可靠关联时先展示待核对，不按标题相似度自动合并。
4. 新增runtime/plan_quality.py或复用短期同名模块：程序检查预算合计、ID存在、重复与依赖；无法确定的活动匹配和负荷保留unknown或交给评审。
5. main.py::_review_context_change()增加差异预览，仍由用户显式确认才提交；learning/confirmation.py保持授权语义。
6. 增加Markdown渲染函数供展示；逐步扩大结构化范围，不依靠复杂正则还原任意计划全文。

### 验证与取舍

测试旧任务保留、候选基准过期、非法ID、依赖环、范围超时、取消不改变历史、重复提交、保存失败。已完成安排默认保护；用户明确要求修改时通过单独清晰授权，而不是一概禁止。

先只做诊断；若之后引入Evaluator-Optimizer，最多一次修订，记录原候选/评审/修改结果；程序约束失败不能由模型自述绕过，最终仍需用户确认。未知不强行转通过。

对照同一案例的约束满足、误改任务数、人工编辑量、确认打扰、调用/token/延迟。结构化输出可能增加生成失败率和格式负担，收益不足时保留试点范围。

退出条件：一个反馈只改变相关安排；用户能核验差异；约束失败可定位；旧存档仍可读，不批量重写历史。

## 5. 阶段C：将一个交互子流程迁入LangGraph（第7—9周）

### 为什么迁移

初始三节点已完成，下一次迁移必须证明暂停/恢复和失败定位收益。选择“生成候选 → 校验 → 等待确认 → 提交/拒绝”，不重写资料问答循环。

### 文件与状态

- 新增runtime/revision_graph.py，沿用runtime/orchestration.py的观察方式。
- persistence/checkpoint_store.py、checkpoint_guard.py扩展该子流程兼容契约，区分工作流版本与学习状态修订号。
- 节点状态保存基准修订、候选、检查结果、确认状态、预算和错误；不存模型客户端或可执行对象。
- 采用明确条件边控制失败、unknown、拒绝和提交，不将自然语言回复当状态转换事实。

提交前重新验证基准修订与授权。为提交增加稳定操作ID并明确幂等策略：重复恢复同一已提交操作不得再次改计划。学习状态文件与检查点是不同持久化资源，不能宣称天然原子事务；通过提交结果记录与恢复核对处理不一致。

保留旧实现开关。分别在生成后、确认前、确认后提交前、提交后观察失败等位置注入故障，并独立进程恢复。先解决实际出现的失败窗口，不直接增加分布式任务系统。

退出条件：恢复只执行尚未完成且仍被授权的步骤；拒绝状态不会恢复成批准；质量与旧流程相当；给出恢复节省的调用与新增复杂度。

## 6. 阶段D：可查询、可纠错的长期记忆（第8—12周，可在B稳定后小范围进行）

### 先划分权威来源

| 信息 | 权威来源与用途 |
| --- | --- |
| 当前目标、计划、进度 | LearningState精确读取 |
| 用户确认的反馈 | 正式记录与更正链，保留原话和采用正文区别 |
| 候选与拒绝经过 | 确认回执/历史，不当作已生效事实 |
| 近期讨论 | 历史与摘要，可能有损 |
| 教材事实 | 独立资料索引，重新读取后核验 |

### 分步实现

1. 在现有feedback_history.py、confirmation_history.py上评测明确ID、时间、对象与更正查询。先确认查询能力不足，不重新实现这些工具。
2. 用固定场景测跨会话回忆、时间顺序、知识更新和无依据拒答。区分“当前加载存档没查到”与“用户从未说过”。
3. 确有自然语言召回缺口时新增persistence/long_term_memory.py，将已确认记录的文本和来源ID构成派生索引；按用户/项目/会话范围过滤，不能因相似度高越过隔离边界。
4. 权威记录保存成功后再索引；索引失败可幂等补建，不把索引失败说成反馈未保存。稳定事件ID与记忆ID，不用目标文本或快照文件名充当身份。
5. 更正后保留历史关联；召回时显示记录时间和更正状态，不让旧事实压过新状态。“未被更正”不自动等于“当前有效”。
6. 提供查看、纠错和删除语义；删除覆盖源记录、派生索引与重建策略，避免重建后恢复已删除信息。明确历史备份保留边界。
7. 按预算组织当前状态、相关记忆、资料、近期聊天，分别统计token；不预载全部存档。

暂不新增专门记忆Agent；Mem0或其他库只作可选对照，不能代替领域的确认与来源规则。

退出条件：重启可找回确认信息、最新更正不混淆、范围外记录不泄漏、删除不再召回、未知能拒答，并与无语义索引基线比较质量及成本。

## 7. 阶段E：RAG版本正确性与证据质量（第2—4个月，按失败优先穿插）

### 先补版本契约

修改retrieval/rag.py的索引目录/manifest契约，纳入embedding模型及实际维度、chunk_size/overlap、提取器/索引格式版本。文件内容指纹与配置指纹分开。

配置不兼容时新建索引版本或明确拒绝复用；不把新旧向量混在同一集合。旧manifest需要兼容策略，不能将缺字段静默视为已匹配。重排配置进入实验快照，但仅改变重排不应无故重新向量化。

覆盖模型变化、维度变化、切分变化、文件不变、索引构建中断、删除与缓存失效。候选新版本完成后再切换；旧版本清理采用显式策略，不自动删除个人资料。

### 再按失败类型优化

- 正确证据未进候选池：检查切分、词法/向量召回与过滤。
- 候选有证据但排名靠后：评估融合与重排。
- 排名前列但正文不充分：精确读取、相邻上下文、截断提示。
- 原文充分但回答错误：生成约束与独立引用支持评审。

复用retrieval/lexical_retrieval.py、retrieval_fusion.py、reranking.py及evaluation/pdf_rag_eval.py，不重复建设混合召回。保留dense/hybrid、重排关闭/聊天/专用后端对照，固定候选池或明确候选池差异。

评价候选覆盖、排名、最终上下文覆盖、具体论断支持、拒答、总成本和延迟。页级命中与引用标记存在不是语义支持；扫描/OCR和表格只有真实资料需求出现后再扩大。

退出条件：能解释一次检索失败发生在哪层；不同配置不会误用旧索引；至少一组独立案例证明某项改动收益或明确无收益。

## 8. 阶段F：工具修正、MCP与多Agent（第3—5个月）

工具调用继续用固定案例衡量：工具选择是否正确、字段错误后能否修正、信息不足是否澄清、预算是否守住。有界ValidationError反馈已存在，只需对照修正率与额外调用，不再无条件增加提示词或额度。

MCP保留local默认、stdio可选，复用现有mcp_compare。只有远程工具或更多客户端复用需求出现后才扩展认证、传输和发现能力。运行中断连与资源释放若出现真实问题，独立故障测试修复，不把当前启动分类当所有故障已覆盖。具体协议实现依据锁定SDK/协议版本。

多Agent先验证生成候选与独立评审分工：输入范围、输出schema、证据ID、错误和预算明确，主控唯一持有学习状态写权限。比较单Agent、固定生成评审链与按需Supervisor；不同时引入Hierarchical和Swarm。

Supervisor表示主控选择专家；只有角色隔离、独立资料或并行工作带来收益才拆。相同模型多角色不保证偏差独立。没有质量收益时保留更简单流程，同样形成工程结论。

退出条件：有同题对照、公开简短决策依据、无私有思维链；能解释额外token、延迟、协调失败和为何选择/放弃多Agent。

## 9. 贯穿所有阶段：评测、持续集成与演示（第1—6个月）

### 统一实验清单

逐步扩展evaluation/runner.py或新增共享记录模块，包含案例/运行ID、模型与服务角色、提示词/代码/资料/配置版本、dirty状态、执行事实、终止原因、判定与缺失用量。主回答、重排、摘要、评审开销分开，避免重复计入嵌套耗时。

历史实验不回填新成绩；校准集与留出集分开；原始Judge判定与规则后判定分开。样本不足时报告计数与逐例结果，不用最佳一次代表稳定收益。

### CI与发布

先检查已有.github/workflows再补缺：离线测试、包导入/CLI烟测、配置边界。在线评测显式手动触发，密钥走受控配置，不让PR自动花费或输出原文。

为每个里程碑保存可公开的小型自有资料、固定输入、脱敏结果摘要与失败示例。README区分已实现/实验中/规划；docs/demo-and-acceptance.md给可重现的3—5分钟展示，不隐藏失败，不把录屏说成本次实时运行。

### 实习作品验收

至少准备四段讲述：

1. 工具schema、调用ID回传、参数纠正和预算终止。
2. full/window/summary在相同对话中的信息保真与成本。
3. 反馈约束冲突如何被发现，候选如何核验和提交。
4. 保存/检查点恢复和MCP接入分别解决什么问题，以及未解决什么问题。

每段附“失败输入 → 设计选择 → 代码路径 → 对照 → 取舍”，不以测试数量、引用数量或框架数量单独证明质量。

## 11. 排序与停止规则

默认顺序：A评测与记忆 → B结构化修订 → C交互恢复；D长期记忆和E索引/证据按已确认失败穿插；F多Agent最后。

若索引配置变化已造成错误复用，E中的版本正确性立即前移；若摘要错误导致事实丢失，先修记忆，暂缓计划结构改造；若质量评测尚不可信，不扩自动循环。

每阶段完成即停止扩范围并形成报告。需要新用户需求、反复失败或可测收益才开启下一轮；不为路线图日期强行叠加新架构。
