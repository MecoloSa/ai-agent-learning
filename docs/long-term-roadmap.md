# 项目长期完善路线：从可运行 Agent 到可评测的工程作品

> 面向目标：2027 年 Agent 工程或相关方向实习  
> 规划方式：按能力门槛推进，不把日期写死。上一阶段通过验收后再进入下一阶段。  
> 核心主线：评测基线 → 状态化编排 → 长期记忆 → MCP → 有依据的多 Agent。

## 1. 项目最终定位

将当前“本地资料分析与学习计划助手”建设成一个可以同时展示 Agent 原理、工程质量和实验方法的作品：

- 有固定 `pipeline` 基线，也有自主工具调用的 `agent` 路径；
- 能处理不同规模和类型的资料，回答带可核验引用；
- 能管理多轮会话状态，并在跨会话场景下使用可控的长期记忆；
- 能以本地 Function Calling 和 MCP 两种方式接入同一类工具并比较取舍；
- 能用 LangGraph 展示显式状态、条件边、失败恢复和断点续跑；
- 只在单 Agent 出现明确瓶颈时引入多 Agent，并有通信协议和消融实验；
- 所有重要改动都有固定数据集、结构化轨迹和质量/成本/延迟报告。

最终作品不以“用了多少框架”为标准，而以“问题定义清楚、控制流可靠、指标可复现、取舍讲得明白”为标准。

## 2. 当前能力与目标能力差距

| 能力 | 当前基线 | 长期目标 | 优先级 |
| --- | --- | --- | --- |

| RAG | 已有完整基础链路和引用元数据 | 固定检索评测、可选混合检索/重排、忠实度评测和参数实验 | P0 |
| Agent 评测 | 有日志，缺少数据集和统一 runner | 规则 + 检索指标 + 人工抽检 + LLM-as-Judge 的分层体系 | P0 |
| 短期 Memory | 已有 `full/window/summary` | 状态与聊天历史分离，完成量化对照 | P0 |
| LangGraph | 依赖已安装，尚无状态图 | 与现有路径并存的显式图编排、持久化、恢复和可观测性 | P1 |
| 长期 Memory | 尚未形成跨会话记忆闭环 | 用户事实/偏好/进度的提取、检索、更新、遗忘和隐私控制 | P1 |

## 3. 分阶段路线

## 阶段 A：评测与可靠性底座

**建议周期**：2～3 周。  
**进入条件**：当前程序能本地运行。  
**退出条件**：任何核心优化都能在固定案例上与基线比较。

### A1. 测试分层

- 单元测试：路径、配置、Memory、阈值过滤、去重、引用解析；
- 控制流测试：Agent 工具调用、错误观察、重试、重复调用、最大轮数和强制收束；
- 集成测试：用假 LLM/Embedding 跑完整链路，不访问网络；
- 少量在线 smoke test：验证真实模型协议兼容，单独标记并默认跳过；
- 端到端评测：在固定资料和问题上比较 `pipeline` 与 `agent`。

### A2. 评测体系

分四层，越靠下越昂贵：

1. **确定性规则**：输出结构、天数、引用格式、来源存在、路径安全、是否正常终止；
2. **检索指标**：Recall@K、MRR、命中覆盖、无结果率、上下文长度；
3. **人工抽检**：引用是否真的支持结论、计划是否可执行、是否遗漏关键主题；
4. **LLM-as-Judge**：仅评价难以规则化的完整性、相关性和可执行性，并保留评分理由、模型版本和人工校准结果。

LLM-as-Judge 至少要做顺序交换测试、少量人工一致性检查和评分失败回退，避免把 Judge 当成绝对真值。

### A3. 结构化运行轨迹

定义 `RunTrace`，保存事件而不是私有思维链：

```text
run_started
model_requested / model_responded
tool_requested / tool_succeeded / tool_failed
retrieval_completed
state_updated
run_terminated
```

每个事件包含时间、阶段、调用编号、脱敏参数摘要、耗时、token、结果大小和错误类型。轨迹既用于调试，也作为评测输入。

### A4. 本阶段作品证据

- `eval/cases/` 版本化数据集；
- 一条命令执行的评测 runner；
- `baseline-v1` 报告；
- 至少一次参数或提示词改动的 A/B 报告；
- 覆盖正常、边界和失败路径的测试。

**面试可讲述点**：为什么离线测试使用 Fake LLM；为什么规则评测优先于 Judge；如何避免提示词改动造成不可见回归。

## 阶段 B：RAG 质量闭环

**建议周期**：2～3 周。  
**进入条件**：已有固定检索标注和 baseline。  
**退出条件**：每项检索策略都有消融结果，不凭直觉保留。

### B1. 先完善现有链路

- 验证不同文件格式的加载质量和 metadata 完整性；
- 比较 chunk size/overlap、绝对阈值、相对阈值、K 和邻居窗口；
- 检查多查询轮询是否提高主题覆盖，同时是否牺牲前排相关性；
- 将“直接命中”和“邻居补充”分别统计，避免邻居被误算为检索成功；
- 对引用做可验证映射，检查 `source/page/chunk` 能否回到原文。

### B2. 再决定是否引入高级检索

只有 baseline 暴露明确问题时才增加：

- 精确名称或代码符号召回差：增加 BM25/关键词检索形成 Hybrid Search；
- Recall@K 尚可但 MRR 低：加入 reranker；
- 查询表达与资料术语错位：做 query rewrite，但记录原查询和改写查询；
- 跨 chunk 上下文经常断裂：优化父子块或章节级索引，而不是无限扩大邻居窗口。

### B3. 关键指标与决策门槛

- 主要看 Recall@K、MRR、证据支持率；
- 同时约束 P95 检索耗时、Embedding 调用量、上下文 token；
- 高级策略只有在固定集上稳定提升，且成本增长可接受时才默认开启；
- 所有实验保留简单策略开关，确保能做消融和回退。

**面试可讲述点**：加载 → 切分 → 向量化 → 召回 → 过滤/重排 → 上下文组织 → 生成 → 引用 → 评测的完整数据流。

## 阶段 C：用 LangGraph 显式化 Planning & Execution

**建议周期**：2～3 周。  
**进入条件**：现有 `pipeline` 和 Agent 循环已有测试及指标。  
**退出条件**：LangGraph 版本能与旧版公平对比并支持失败恢复。

### C1. 不替换旧实现，新增实验模式

建议新增 `--orchestrator legacy|langgraph`，保留当前 `pipeline` 与自主工具循环。第一版状态可以包含：

```text
goal
material_dir
mode
material_overview
evidence
analysis
plan
tool_trace
retry_count
errors
termination_reason
```

建议节点：`validate_input → route_materials → collect_or_retrieve → analyse → validate_analysis → plan → validate_plan → persist`。

条件边只根据可观察状态跳转，例如“资料是否有效”“证据是否足够”“校验是否通过”“是否还能重试”。不要把模型私有思维链写进状态。

### C2. 状态、计划和执行的边界

- **计划**：可显示的步骤列表、负责人、状态和完成条件；
- **行动**：一次模型或工具调用；
- **观察**：工具结果、错误、评分或校验结果；
- **终止**：成功、预算用尽、不可重试错误、用户取消。

这就是本项目中可落地的 ReAct 思想。CoT/ToT 可以作为学术概念理解，但工程实现应记录结构化决策事实，不要求或保存模型私有推理文本。

### C3. 必须验证

- 同一输入下 legacy 与 LangGraph 的任务成功率、耗时、token 和失败恢复率；
- 节点失败后能否从 checkpoint 继续，而不是整条链重跑；
- 状态 schema 变化是否有兼容策略；
- 图变复杂后，可观测性是否真的提升。

**面试可讲述点**：LangGraph 解决的是显式状态、条件路由、持久化和恢复，不是简单把函数包装成节点。

## 阶段 D：长期记忆闭环

**建议周期**：2～3 周。  
**进入条件**：短期 Memory 对照实验完成，状态 schema 稳定。  
**退出条件**：跨会话记忆有更新、遗忘、隐私和评测机制。

### D1. 先定义“值得记住什么”

建议只保存明确、可复用的信息：

- 用户长期学习目标；
- 稳定偏好，如解释深度、每日可用时间；
- 已完成主题和评测结果；
- 用户明确确认的约束。

原始聊天全文、模型猜测、一次性临时问题默认不进入长期记忆。

### D2. 记忆对象建议

```text
memory_id
user_id
type: preference | goal | progress | constraint
content
source_turn
confidence
created_at / updated_at / expires_at
status: active | superseded | deleted
```

向量库只负责相似检索；结构化数据库负责身份、版本、覆盖、删除和审计。二者共同组成长期记忆，不应混为一谈。

### D3. 完整闭环

`候选提取 → 规则/模型判断是否写入 → 去重或覆盖旧记忆 → 检索 → 相关性与权限过滤 → 注入上下文 → 用户修正/删除 → 评测`

### D4. 评测案例

- 数天后仍能恢复稳定偏好；
- 用户改变目标后旧记忆不再主导回答；
- 不相关会话不召回；
- 用户要求删除后不可再检索；
- 错误记忆可追踪到来源并修正。

**指标**：记忆精确率、召回率、过期信息率、错误覆盖率、额外 token、写入/召回耗时。

**面试可讲述点**：为什么聊天历史不等于长期记忆；如何解决记忆冲突、遗忘和隐私。

## 阶段 E：MCP 对照实现

**建议周期**：2 周。  
**进入条件**：现有工具接口稳定、测试完善。  
**退出条件**：同一业务能力能通过本地 Function Calling 和 MCP 两种通道调用。

### E1. 最小范围

把只读工具优先暴露为本地 MCP Server：

- `list_learning_files`
- `read_learning_file`
- `search_learning_files`
- `retrieve_learning_context`

保留相同输入输出语义和路径安全边界。MCP Client 只负责发现 schema、调用和结果适配，不能绕过已有安全校验。

### E2. 要掌握的协议要点

- Server 如何声明工具名称、描述与 JSON Schema；
- Client 如何发现工具并转换为模型可调用形式；
- 请求、结果和错误如何传输；
- 连接生命周期、超时、取消和版本兼容；
- Resources/Prompts 与 Tools 的职责差异。

### E3. 对照实验

比较本地 Function Calling 与 MCP：

- 工具发现与接入成本；
- 参数校验和错误表达；
- 单次调用额外延迟；
- 可测试性与进程隔离；
- 跨应用复用能力。

**面试可讲述点**：Function Calling 是模型如何表达“我要调用什么”，MCP 是应用如何标准化提供和调用外部能力；两者互补，不是替代关系。

## 阶段 F：有证据地引入多 Agent

**建议周期**：2～3 周。  
**进入条件**：单 Agent 已有稳定评测，且发现职责冲突、上下文污染或可并行瓶颈。  
**退出条件**：多 Agent 在至少一个主要指标上有稳定收益，且成本透明。

### F1. 首选 Supervisor，而不是直接 Swarm

本项目建议第一版角色：

- Supervisor：维护任务状态、路由和终止条件；
- Retrieval Agent：只负责证据召回与引用，不生成最终计划；
- Analysis Agent：基于证据形成知识结构；
- Planning Agent：基于分析和证据生成学习计划；
- Critic/Validator：执行规则校验或指出缺失，不直接无限反思。

状态所有权由 Supervisor/共享图状态管理。Agent 之间传递结构化结果和引用 ID，不复制全部对话。

### F2. 三种模式的学习顺序

1. **Supervisor**：中心节点分派任务，适合本项目的可控流程；
2. **Hierarchical**：任务和团队规模变大后，再尝试分层主管；
3. **Swarm**：Agent 根据 handoff 自主交接，灵活但更难测试，只作为实验分支。

### F3. 必做消融

至少比较：单 Agent、Supervisor 多 Agent、去掉 Critic、去掉并行检索。观察任务完成率、证据支持率、延迟、token、交接错误和重复工作率。

如果多 Agent 质量没有显著提升，或成本/延迟增长不可接受，就保留单 Agent 为默认。这是有价值的工程结论，不是失败。

**面试可讲述点**：什么时候不该拆 Agent；上下文隔离、状态所有权和通信协议为何比 Agent 数量更重要。

## 阶段 G：作品集与求职收口

**建议周期**：持续进行，投递前集中整理 1～2 周。

### G1. 仓库应具备

- 清晰的快速开始和架构图；
- 已实现/实验中/规划中的能力表；
- 可下载或可生成的小型脱敏评测集；
- baseline 与关键优化报告；
- 一条命令运行单测，一条命令运行离线评测；
- 真实在线评测需要哪些密钥、费用和时间的说明；
- 已知限制、安全边界和失败示例。

### G2. 建议准备的演示

1. 小资料走直接读取，大资料自动切换 RAG；
2. Agent 选择工具、发生一次错误并依据观察恢复；
3. `pipeline` 与 `agent` 同题对比；
4. 三种短期 Memory 的 token/信息保真对比；
5. LangGraph checkpoint 恢复；
6. 本地工具与 MCP 工具的等价调用；
7. 一张评测仪表板或 Markdown 报告展示改造前后变化。

### G3. 面试叙事模板

按“问题—基线—假设—改动—评测—结果—取舍—下一步”讲述。例如：

> 多查询召回提高了主题覆盖，但也增加重复 chunk。我先用 Recall@K 和跨查询重复率建立基线，再使用轮询合并与去重；固定集上覆盖率提升、上下文长度受控，因此保留该策略。对于 MRR 仍低的案例，下一步才考虑 reranker。

这样的叙事比“我用了 LangChain、LangGraph、MCP”更能体现工程能力。

## 4. 长期指标看板

| 类别 | 核心指标 | 说明 |
| --- | --- | --- |
| 任务质量 | 任务完成率、计划结构通过率、约束满足率 | 首先保证系统完成用户任务 |
| 证据质量 | Recall@K、MRR、引用存在率、引用支持率 | 区分检索问题与生成幻觉 |
| Agent 行为 | 工具成功率、重复调用率、强制终止率、恢复率 | 衡量工具循环是否稳定 |
| Memory | 事实保留率、过期信息率、错误召回率 | 同时衡量记住和正确遗忘 |
| 一致性 | 多次运行得分均值与方差 | 防止只展示一次幸运结果 |
| 性能成本 | P50/P95 延迟、模型调用数、token、费用 | 质量提升必须说明代价 |
| 工程质量 | 测试覆盖的行为、可复现率、失败可诊断率 | 不盲目追求单一覆盖率数字 |

每轮优化只设一个主指标和若干护栏指标。例如优化召回时以 Recall@K 为主，同时保证 P95 延迟和上下文 token 不超过约定预算。

## 6. 优先级与暂停规则

以下情况出现时，应暂停增加新能力：

- 现有测试不稳定或关键分支没有测试；
- README、配置和运行行为不一致；
- 评测集不足以证明新策略效果；
- 工具或模型错误无法从轨迹定位；
- 新框架只能增加代码量，不能改善状态、恢复、质量或可维护性；
- 多 Agent 只是把原有顺序函数换成多个角色名称。

暂停不是停滞，而是回到最近一个可复现版本，补足证据后再推进。

## 7. 注释与动态评估约定

后续新增或实质修改的关键逻辑，邻近注释应优先回答：

- 为什么需要这个分支、阈值、重试或终止条件；
- 输入、状态和输出如何流动；
- 哪种边界或失败模式最危险；
- 应观察哪个日志或指标，什么现象意味着需要调参或回退。

示例：

```python
# 动态评估：同时观察无结果率和 Recall@K。
# 无结果率上升且 Recall@K 下降，通常说明阈值过严；
# 上下文显著增长但 Recall@K 不变，则不应继续扩大 k。
```

## 8. 推荐学习顺序

与项目同步学习，避免理论和代码脱节：

1. Function Calling 消息协议、工具 schema、错误观察和循环终止；
2. RAG 全链路及 Recall@K/MRR；
3. 短期 Memory 与上下文预算；
4. Agent 自动评测、人工抽检与 LLM-as-Judge 校准；
5. LangGraph 状态、节点、条件边、checkpoint；
6. 长期记忆的数据模型、更新/遗忘和隐私；
7. MCP Client/Server、工具发现和协议错误；
8. Supervisor 多 Agent，再学习 Hierarchical 与 Swarm。

每学完一个主题，都应在本项目中留下四样东西：一个小实现、一组测试、一份对照数据、一段能讲清取舍的文档。这四项共同构成实习面试中最可信的项目证据。
